# Go 支付与履约系统设计

## 1. 目标

将现有 `Go_demo2` 从 User/Product 微服务练习升级为可公开展示的支付与履约后端。项目模拟微信和支付宝的真实交互特征，但不使用真实 SDK、商户密钥或实习公司的代码与数据。

项目重点证明以下能力：

- Kratos v2 模块化服务设计；
- PostgreSQL 事务、唯一约束、条件更新与任务领取；
- 支付下单、异步回调、退款、履约和主动对账；
- 幂等、状态机、重复通知、超时与异常恢复；
- Redis 限流与快速去重，但不将其作为最终一致性来源；
- 从单元测试、数据库集成测试到端到端测试的完整验证。

## 2. 范围

### V1 包含

- `commerce` 模块化单体服务；
- `order`、`payment`、`refund`、`fulfillment`、`reconciliation`、`admin` 六个领域模块；
- 独立 `mockpay` 服务，模拟微信与支付宝；
- PostgreSQL、Redis、Docker Compose；
- HTTP/gRPC API；
- 异步支付及退款回调；
- 数据库任务表驱动的履约 Worker；
- 主动查询和人工补偿；
- CI、故障场景测试、基础指标与项目文档。

### V1 不包含

- 真实微信或支付宝密钥；
- 前端管理后台；
- Kafka、Kubernetes、真实资金结算；
- 将交易主流程提前拆成多个微服务；
- 仅为了展示技术栈而增加的组件。

### V2 可选

- Transactional Outbox；
- RabbitMQ Publisher 与履约 Consumer；
- Prometheus、Grafana、OpenTelemetry；
- 将 `fulfillment` 拆成独立服务。

## 3. 架构

```text
Client / Admin
      | HTTP
      v
Commerce Service
|- order          业务订单与订单状态机
|- payment        支付单、渠道接口、回调处理
|- refund         退款单与退款状态机
|- fulfillment    履约任务与重试 Worker
|- reconciliation 主动查询与状态修正
`- admin          异常查询与人工补偿
      |                 |
      | PostgreSQL      | HTTP/gRPC
      v                 v
 PostgreSQL          MockPay Service
 Redis               |- WECHAT
                     `- ALIPAY
```

`commerce` 第一版保持单服务，因为订单、支付、退款和履约任务创建需要清晰的本地事务边界。`mockpay` 独立部署，用来制造真实外部系统会出现的成功、失败、超时、重复通知和通知丢失。

## 5. 数据模型

- `id BIGSERIAL PRIMARY KEY`
- `order_no VARCHAR(32) UNIQUE NOT NULL`
- `user_id BIGINT NOT NULL`
- `amount_cents BIGINT NOT NULL CHECK (amount_cents > 0)`
- `status VARCHAR(32) NOT NULL`
- `version BIGINT NOT NULL DEFAULT 0`
- `created_at TIMESTAMPTZ NOT NULL`
- `updated_at TIMESTAMPTZ NOT NULL`

### `payment_attempts`

- `id BIGSERIAL PRIMARY KEY`
- `payment_no VARCHAR(32) UNIQUE NOT NULL`

- `channel VARCHAR(16) NOT NULL`

- `id BIGSERIAL PRIMARY KEY`
- `channel VARCHAR(16) NOT NULL`

- `payment_no VARCHAR(32) NOT NULL`
- `raw_payload JSONB NOT NULL`
- `process_status VARCHAR(32) NOT NULL`
- `received_at TIMESTAMPTZ NOT NULL`
- `UNIQUE(channel, callback_id)`

### `refunds`

- `id BIGSERIAL PRIMARY KEY`
- `refund_no VARCHAR(32) UNIQUE NOT NULL`
- `payment_id BIGINT NOT NULL REFERENCES payment_attempts(id)`
- `amount_cents BIGINT NOT NULL CHECK (amount_cents > 0)`

### `fulfillment_tasks`

- `id BIGSERIAL PRIMARY KEY`
- `order_id BIGINT UNIQUE NOT NULL REFERENCES orders(id)`

### `outbox_events`

- `aggregate_id VARCHAR(64) NOT NULL`
- `event_type VARCHAR(64) NOT NULL`
- `payload JSONB NOT NULL`
- `status VARCHAR(32) NOT NULL`
- `attempts INT NOT NULL DEFAULT 0`
- `next_retry_at TIMESTAMPTZ NOT NULL`
- `created_at TIMESTAMPTZ NOT NULL`

## 6. 状态机

```text
Order:
CREATED -> PAYING -> PAID -> FULFILLING -> COMPLETED
                    |           `-------> FULFILL_FAILED
                    `-------------------> REFUNDING -> REFUNDED

Payment:
CREATED -> PROCESSING -> SUCCEEDED
                     |-> FAILED
                     `-> CLOSED

Refund:
CREATED -> PROCESSING -> SUCCEEDED
                     `-> FAILED
```

状态变更必须采用带来源状态的条件更新。影响行数为零时，业务层区分重复事件、对象不存在和非法状态转换。

## 7. 幂等设计

- 客户端为支付和退款提供 `Idempotency-Key`；
- 服务端根据稳定字段生成 `request_fingerprint`；
- 相同幂等键和相同 fingerprint 返回第一次结果；
- 相同幂等键但 fingerprint 不同返回 `IDEMPOTENCY_KEY_REUSED`；
- PostgreSQL 唯一约束是并发场景下的最终保障；
- Redis可用于短期快速命中，但Redis不可用时接口仍保持正确；
- 渠道支付单使用稳定的 `payment_no`，外部调用超时后使用该编号主动查询，禁止盲目创建新渠道单。

## 8. 回调事务

一次支付成功回调在同一 PostgreSQL 事务中完成：

1. 插入 `payment_callbacks`；
2. 条件更新 `payment_attempts`；
3. 条件更新 `orders`；
4. 插入唯一 `fulfillment_tasks`；
5. 插入 `outbox_events`；
6. 提交事务。

重复回调命中唯一约束后返回成功确认，不重复生成履约任务。回调只持久化状态和任务，不直接执行耗时发货。

## 9. 履约与补偿

V1 Worker通过以下模式领取任务：

```sql
SELECT id
FROM fulfillment_tasks
WHERE status IN ('PENDING', 'RETRY')
  AND next_retry_at <= NOW()
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT $1;
```

成功后将订单推进到 `COMPLETED`；失败时增加 `attempts` 并计算下一次重试时间。超过最大次数进入 `FULFILL_FAILED`，由 Admin人工重试。

主动对账任务查询长时间处于 `PROCESSING` 的支付或退款单，通过 `PaymentGateway.QueryPayment` / `QueryRefund` 修正本地状态。

## 10. MockPay

MockPay提供微信、支付宝两个渠道，并支持按请求参数选择场景：

- `success`
- `failure`
- `delayed_callback`
- `duplicate_callback`
- `lost_callback`
- `response_timeout_after_success`
- `refund_callback_lost`
- `invalid_amount`

MockPay保存渠道交易状态，以便 commerce主动查询。所有签名仅使用项目自定义测试密钥模拟，不能复刻公司的协议或配置。

## 11. 测试策略

### 单元测试

- 状态机合法和非法转换；
- fingerprint稳定性；
- 金额和参数校验；
- 渠道选择；
- 退避时间计算。

### PostgreSQL集成测试

- 同一幂等键并发请求只创建一条支付单；
- 同键不同参数被拒绝；
- 重复回调只产生一个履约任务；
- 条件更新防止状态回退；
- `SKIP LOCKED`不重复领取任务；
- 事务中任一步失败时全部回滚。

### 端到端测试

- 下单、支付、回调和履约；
- 十次重复回调只发货一次；
- 回调丢失后主动查询修复；
- 履约失败后重试成功；
- 支付成功后完成退款。

### AI协作约束

AI可以生成测试骨架、Mock和样板代码，但每个测试完成前，开发者必须：

1. 先用自然语言写出被保护的业务规则；
2. 逐条解释Arrange、Act、Assert；
3. 故意破坏生产实现并确认测试失败；
4. 恢复实现并确认测试通过；
5. 在Issue中记录一个自己补充的边界场景。

## 12. 验收标准

- `docker compose up`可以启动 PostgreSQL、Redis、commerce和mockpay；
- `go test -race ./...`通过；
- `go vet ./...`通过；
- smoke脚本跑通支付成功和退款闭环；
- 重复回调不会产生重复履约；
- Redis停止后支付幂等仍然正确；
- MockPay回调丢失后可通过主动查询恢复；
- README包含架构、状态机、启动方式、故障演示和测试说明；
- 公开版本不包含实习公司的源码、命名、数据、密钥和内部文档。
